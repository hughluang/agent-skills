# 核实再规划

用户把某件事当作需要处理的问题时，先独立核实其中每条主张，再列出真正要解决的问题并规划方案。包装形式不改变程序：主张里的因果与修法默认是待证假设，不是开工依据。

成功标准：进入规划的每一项都有离开原主张表述的证据；方案收口的是不变量，不是把当前被指出的表象压回去。

**是否适用**：若接下来要按该主张判断存在与否、归因、该不该改或怎么改，就必须走本流程。不问主张来自问句、抱怨、清单、审查、报告还是点名的根因。来源不授予可信度。

## 1. 主张不是事实

对每一条主张独立取证。证据必须能离开原表述复核：只看系统现状、不依赖主张原文，也能得出同一事实。

**成立判定**：列得出验证方法、且该方法能产生可观察事实，才进入核实。否则状态是「未核实」，不得当作成立，也不得进入规划。无法判定时倒向「未核实」。

核实要做的：

- 按主张所指的对象去系统里核对，而不是按主张所给的修法去搜代码再反推根因。
- 按机制计数：同一机制的多种表象是一条；条数不由原主张的条数决定。
- 现象与机制分列，不糊成一句「成立」。
- 因果链逐步落到证据；走不通的跳步保持为未核实，不用「看起来像」「通常会」补上。

诊断手段（复现、对照、收窄输入）服务于核实，不替代核实。即便现象已经能稳定复现，仍先问主张是否成立、机制是否完整，再进入诊断循环。

## 2. 三条为什么，逐步下挖

对每条主张依次追问，每问都必须落到证据，不得跳步：

| 问 | 要拆开的对象 |
|---|---|
| **为什么会提出这个缺口或问题** | 提出者依据什么把它标出来：观察了哪条路径、断言的是什么、缺了哪条对照。提出所用的标准与要保护的不变量不一致时，标出来的不一定是真问题。 |
| **为什么产生** | 系统里哪一次决策、哪条契约、哪层越权，使该现象成为必然而非偶发。 |
| **为什么问题成立** | 在已核实的机制下，它是否仍构成需要解决的问题；成立的是哪一层（契约、状态机、完整性），而不是原标题。 |

下挖：

- 现象与机制分列。现象对、机制不完整 → 按机制继续挖，不按原处方停。
- 两条观察不能同时对同一条活路径成立时，优先解释为路径分裂或失败被计成另一种成功，而不是局部公式写错。
- 同一机制下、原主张未写但可复现的路径，记为同源漏测，并进同一问题。
- 把错误行为锁成「正确」的测试与对照，是机制的一部分，不是旁证。

写核实结论时分列现象、机制、是否仍成立，不写成一句总评。

## 3. 列出需要解决的问题

核实结束后才列问题。列表来自机制，不必与原主张条目一一对应：

- 同一机制的多种表象合并
- 主张未写的同源漏测补入
- 主张当缺陷、核实后属于预期契约、产品选择或提出标准本身有误的，标明「保持」，不进入修复范围
- 每项写：成立的是什么、要收口的是哪条不变量，而不是把某症状压回去

此列表是规划的输入。未进入列表的原处方，实现时不得偷做。

## 4. 规划从结构上解决

针对列表中的不变量设计方案。

**结构 vs 兜底**：若方案在保留原机制裂缝的前提下，只让当前被指出的表象消失，它就是兜底——换一条同源输入仍会坏。结构解改变的是权责与契约：不变量由谁持有、失败如何被看见、声明的约束是否覆盖所有读写路径。

规划必须带「明确不做」：把核实阶段已排除的处方写成约束，实现中途想加回去时停下来。锁死旧行为的测试随结构一起改预期，不能当回归绿。

接口或模块边界需要分叉时，用同一约束集做互不抄袭的方案并逼收敛；不要为系统中尚不存在的能力预先公开调用方契约。

## 5. 开工闸门

复制并勾选；未全勾不得改代码（用户明确只要核实结论时，停在第 3 步）：

- [ ] 每条主张都有离开原表述的证据，或已标为不成立 / 保持
- [ ] 三条为什么已逐步写到机制，没有用原主张里的根因顶替
- [ ] 现象、机制、同源漏测分列，没有糊成「成立」
- [ ] 需要解决的问题来自机制，且已标出不做的原处方
- [ ] 方案收口的是不变量，不是堆砌兜底；「明确不做」已写进计划
