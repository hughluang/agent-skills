# 实质收拢

## 目标

把一组变更收拢到「每个保留下来的单元都持有真实决策或变换」的状态。

交付物是已经收拢好的代码：已证实的问题直接改掉，并用测试或引用检索确认规则重新成立。审查只是取证手段，问题清单本身不是交付物；只发现不修改，不算完成。

## 范围

对照变更范围（未提交 diff、暂存区、指定提交或 PR），只处理违反下列规则且可由代码路径证实的问题。不扩大到变更未触及的既有债务，除非它阻塞理解当前变更。变更引入的、或因变更而失去入边/失去生产者的代码，均在范围内。

测试代码只当作调用方：生产代码收拢时，引用被删、下沉或改签名符号的测试一并修改或删除；不对测试代码本身套用下列规则。

## 规则

每条规则是一条可证伪的不变量。用事实证明它成立或失败；不得靠情景类比或未列出的例子去猜「算不算」。

1. **单元有实质**：每个新增或改动的公开单元，必须持有一层无法无损下沉的决策、不变量或变换。
   证伪：删掉该单元、将其体直接接到调用方后，可观察行为不变。

2. **分支有结果**：每个分支必须被某组可达输入命中，且命中后的可观察结果与其他分支不同。
   证伪：写不出这样的输入，或写出后结果与另一分支相同。

3. **兜底有后继**：每条降级或吞错路径必须对应已定义且可达的失败态，并转入可被观察的后继。
   证伪：该路径可走，但调用方无法从结果中区分「失败已处理」与「成功或未发生」。

4. **包装有边界职责**：包装层必须在接缝上改变契约。
   证伪：去掉包装后，调用方与下层的契约与可观察行为均不变。

5. **依赖显式**：协作对象必须从调用点的签名即可读出。
   证伪：缺省该参数后，实现仍能从签名以外的地方解析到同一对象。

6. **代码有入边**：每个被保留的符号必须能从变更后的可达根沿引用到达。可达根是仍对外暴露或仍被生产路径引用的入口；仅被测试或死代码引用，不算有入边。
   证伪：从可达根沿引用走不到该符号。此为孤立代码，应删除。

7. **域有栖居**：代码所处理的每一种可区分情形，必须能由变更后仍存在的生产者构造出来。
   证伪：该情形没有生产者，或所有生产者已不可达。此为死域；只为它服务的代码应一并删除。

## 做法

1. **取证。** 取得完整 diff，列出改动的公开符号及其调用方/被调用方，对照全部规则下判。
2. **每项问题用代码路径证明**：指出使哪条规则失败的那组事实。
3. **分歧用事实收束。** 同一组事实可推出相反结论、或判断内部互相矛盾时，先确定「用什么办法能验证分歧」并执行，直到得到可复核的事实。列不出验证方法、或方法不能产生事实，就还在猜测，不得下判。不得用「可能」「也许」「看起来」择一或调和。
4. **按依赖顺序收拢。** 被依赖的删除或下沉先做，让前一步不会使后一步失效；同一层内先改会误导边界或掩盖错误的问题。每项改动连同受影响的调用方与测试一起改完，不留半截状态。
5. **确认规则重新成立。** 每项改动后跑相关测试、类型检查或 lint，并重走引用检索，确认被删符号无残留引用、行为未变或按预期改变。验证失败就继续修，不得把失败留给后续。

## 收尾

简要说明结果：改了哪些地方、各自对应哪条规则、用什么验证过。末尾用一两句给出总判：变更主旨是否成立、收拢后变更成了什么样子。

**不确定时不动手**：判不准是否违规的，不改代码，单独列出——写清双方主张、已做的验证、还缺的事实，以及要执行什么才能定夺。禁止靠猜测改代码。

全部规则均成立时不改代码：明说无需收拢，并给出支撑此判断的事实。
